# Deploy da revisão de 2026-10-27 (commits 2e8f721..f90a6e3)

Rodada de correções de auditoria: segurança (SEC-06, SEC-08, SEC-09, SEC-10), banco (DB-01..08),
gateway (GW-01..15), automações (AUT, EST), frontend (FE-01..11) e infra (OPS). A ordem abaixo
é obrigatória. Tudo roda na VPS, como o usuário de deploy, dentro de `~/norvia/interface-web`.

## O que muda para quem opera

- **Exportação da planilha de lançamentos ML** deixou de ser `GET`. Agora é
  `POST /api/ml-reconciliation/analises/{id}/arquivos/lancamentos/exportar` (permissão
  `conciliacao_ml:baixar`, auditada). O `GET .../arquivos/lancamentos` responde `405`. O gateway,
  o financeiro e o frontend mudam juntos: **o frontend novo precisa estar publicado logo após o
  gateway**, senão a tela antiga recebe `405`.
- **Contrato do lote do Marketplace**: `skus`, `produtos` e `anuncios` aceitam no máximo 200 itens
  (`400` acima disso). Painel e automação já respeitam.
- **Circuit breaker**: quando uma automação está fora, o gateway responde `503` com
  `code: "circuit_open"`, e a tela mostra a mensagem própria.
- **Produção só aceita `DATA_MODE=live`** (SEC-10). Se o `.env` do gateway não tiver `DATA_MODE=live`,
  o container não sobe.
- **Contagem de estoque roda em um processo só.** Com `WEB_CONCURRENCY` ou `UVICORN_WORKERS` > 1 o
  serviço se recusa a subir.
- **Fuso e tzdata**: as imagens do gateway, financeiro, marketplace e contagem-estoque têm
  `TZ=America/Sao_Paulo` e instalam `tzdata`.
- **Backup**: retenção mantém os `BACKUP_KEEP_MIN` (padrão 3) backups bem-sucedidos mais recentes,
  e há um teste mensal de restauração (`norvia-backup-verify.timer`).

## Ordem do deploy

### 1. Atualizar o código

```bash
cd ~/norvia/interface-web && git pull --ff-only origin main
git log --oneline -6        # tem que aparecer f90a6e3 no topo
```

### 2. Checar as duas migrações de 2026-10-27 antes de aplicar

As pré-condições estão no cabeçalho de cada arquivo. Se alguma query devolver linhas, a migração
correspondente **aborta**: corrija os dados à mão e só então aplique.

```bash
# 2a) baixas-sucesso-unico: contas com mais de uma baixa com sucesso (tem que vir vazio)
docker compose exec -T -e MYSQL_PWD mariadb mariadb -uroot financeiro -e "
  SELECT empresa, conta_pagar_id, COUNT(*) AS n, GROUP_CONCAT(id ORDER BY id) AS ids
    FROM conciliacao_baixas_historico WHERE status = 'sucesso'
   GROUP BY empresa, conta_pagar_id HAVING COUNT(*) > 1;"

# 2b) indices-sessoes-e-fks-usuarios: autores de aprovação/alteração de permissão que não existem mais (tem que vir vazio)
docker compose exec -T -e MYSQL_PWD mariadb mariadb -uroot financeiro -e "
  SELECT id, aprovado_por, permissoes_alterado_por FROM usuarios u
   WHERE (u.aprovado_por IS NOT NULL AND u.aprovado_por NOT IN (SELECT id FROM usuarios))
      OR (u.permissoes_alterado_por IS NOT NULL AND u.permissoes_alterado_por NOT IN (SELECT id FROM usuarios));"
```

Antes, exporte a senha do root no shell sem deixá-la no histórico:
`read -rs MYSQL_PWD && export MYSQL_PWD` (é o mesmo mecanismo que o `scripts/migrate.sh` usa).

### 3. Aplicar as migrações (antes do gateway)

```bash
cd ~/norvia/interface-web
scripts/migrate.sh                                                       # status: tem que listar as 2 como PENDENTE
scripts/migrate.sh apply database/migrations/2026-10-27-baixas-sucesso-unico.sql
scripts/migrate.sh apply database/migrations/2026-10-27-indices-sessoes-e-fks-usuarios.sql
scripts/migrate.sh                                                       # as duas aparecem como aplicada
```

`migrate.sh apply` mostra o cabeçalho, pede confirmação (`s`), aplica e registra em
`schema_migrations`. Ele tem `flock`: não rode dois `apply` em paralelo.

Se o `apply` avisar que a migração foi aplicada mas o registro falhou, rode
`scripts/migrate.sh mark <arquivo>` depois de confirmar o estado no banco. Não reaplique.

### 4. Rebuild conjunto dos serviços Python e do gateway

Suba os quatro juntos. O gateway, o financeiro e o marketplace usam `AUTOMATIONS_INTERNAL_KEY`,
e o SEC-06 muda o contrato entre gateway e financeiro. `--build` é obrigatório: Dockerfiles,
`requirements.lock` e `tzdata` mudaram.

```bash
cd ~/norvia/interface-web
docker compose up -d --build gateway automacao-nfe automacoes-marketplace contagem-estoque

docker compose ps                                          # os 4 em "healthy" (ou "running" enquanto o health não roda)
docker compose logs --tail=50 gateway automacao-nfe automacoes-marketplace contagem-estoque
curl -s http://127.0.0.1:3100/health                       # {"status":"ok"}
```

Conferências específicas:

```bash
# TZ e tzdata nas imagens
for s in gateway automacao-nfe automacoes-marketplace contagem-estoque; do
  docker compose exec "$s" sh -c 'echo "$TZ"; date'
done
docker compose exec automacao-nfe python -c "import zoneinfo; print(zoneinfo.ZoneInfo('America/Sao_Paulo'))"

# Gateway em live (SEC-10): tem que estar DATA_MODE=live
docker compose exec gateway printenv DATA_MODE

# Contagem: o serviço não pode ter mais de um worker (sem WEB_CONCURRENCY/UVICORN_WORKERS > 1)
docker compose exec contagem-estoque sh -c 'echo "WEB=${WEB_CONCURRENCY:-} UVI=${UVICORN_WORKERS:-}"'
```

Se o `contagem-estoque` não subir, leia o log: a recusa por `WEB_CONCURRENCY`/`UVICORN_WORKERS` > 1
aparece com mensagem explícita. Problemas com `lancamentos_tiny.json` (pasta do registro, `REGISTRO_DIR`)
também aparecem no log de subida.

### 5. Frontend estático (logo depois do gateway)

```bash
cd ~/norvia/interface-web/frontend
npm ci && npm run build
rsync -av --delete --dry-run dist/client/automacoes/ /var/www/automacoes/   # confere o que vai apagar/copiar
rsync -av --delete dist/client/automacoes/ /var/www/automacoes/
```

O destino é sempre `/var/www/automacoes/`. Depois, abra o painel e confira a tela de Conciliação ML:
a exportação da planilha de lançamentos tem que funcionar pelo botão (POST), não por link direto.

### 6. Backup: retenção e teste de restauração

No `backup.env` de produção (o arquivo fica fora do git, `chmod 600`; modelo em
`scripts/backup/backup.env.example`), adicione se não existir:

```env
BACKUP_KEEP_MIN=3
```

Instale o teste mensal de restauração (units em `scripts/backup/systemd/`):

```bash
cd ~/norvia/interface-web/scripts/backup
cp systemd/norvia-backup-verify.service systemd/norvia-backup-verify.timer ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now norvia-backup-verify.timer        # dia 1 de cada mês, 04:30
systemctl --user start norvia-backup-verify.service             # roda agora, pelo systemd
cat ~/backups/norvia/last-verify.json                           # use o BACKUP_DIR do backup.env
```

O teste sobe um MariaDB descartável (`VERIFY_MARIADB_IMAGE`, padrão `mariadb:11`) e precisa de
docker ou podman rootless. A chave `BACKUP_AGE_IDENTITY` só é necessária se o dump estiver em `.age`.
Detalhes em `scripts/backup/README.md`.
